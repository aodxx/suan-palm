# แผนพัฒนา UI/UX สวนปาล์ม V4: แถบไอคอนและเครื่องมือแบบเป็นหมวด

> สถานะ: แผนงานสำหรับพัฒนาต่อจากโค้ดปัจจุบัน  
> เป้าหมาย: ให้สมาชิกครอบครัวใช้ได้ง่ายทั้งมือถือและคอมพิวเตอร์ โดยไม่ต้องเลื่อนหาเครื่องมือสำคัญในแผงยาว  
> หลักการ: ปรับหน้าจอและการเข้าถึงเครื่องมือก่อน ไม่รื้อระบบคำนวณ/แผนที่ที่ทำงานอยู่ และไม่เพิ่ม backend หรือระบบล็อกอินโดยไม่จำเป็น

## 1. สรุปการตรวจโค้ดปัจจุบัน

ไฟล์หลักที่ตรวจ:
- `index.html` — โครงสร้างแผงข้อมูล มีข้อมูลแปลง พื้นที่ จำนวนต้น ราคาต้นกล้า ตั้งค่ากริด ปุ่มสร้างจุดปลูก ปุ่มส่งออก และคำแนะนำอยู่ในหน้าเดียว
- `css/style.css` — Desktop ใช้ sidebar ด้านซ้าย; มือถือใช้ bottom sheet ที่ย่อ/ขยายได้ แต่เมื่อเปิดแผงยังต้องเลื่อนดูเนื้อหาหลายส่วน
- `js/app.js` — จัดการ Leaflet, เครื่องมือวาดขอบเขต, ตำแหน่ง, จุดปลูก, การแก้ไข/ลบ และสถานะการทำงาน
- `js/calculator.js` — สูตรพื้นที่และจำนวนต้น รวมถึงสูตรระยะปลูกสามเหลี่ยมด้านเท่า
- `js/exporter.js` — ส่งออก PDF/รายงาน/CSV/GeoJSON
- `README.md` — อธิบายการใช้ bottom sheet และระบุว่ามีการบันทึกอัตโนมัติใน LocalStorage

### ปัญหาที่ควรแก้ก่อน

1. เครื่องมือวาดอยู่บนแผนที่ แต่เครื่องมือสร้างจุดปลูกอยู่ในแผงข้อมูล ผู้ใช้จึงต้องมองหาคนละตำแหน่ง
2. ข้อมูลสรุปและเครื่องมือปฏิบัติงานถูกวางต่อกัน ทำให้ต้องเลื่อนผ่านเนื้อหาที่ไม่เกี่ยวกับงานในขณะนั้น
3. การตั้งค่าที่ใช้ไม่บ่อย เช่น หมุนแนวแถวและเว้นระยะขอบ ใช้พื้นที่หน้าจอเท่ากับปุ่มหลัก
4. ปุ่มส่งออกหลายรูปแบบและปุ่มล้างทั้งหมดอยู่ในบริเวณเดียวกับงานประจำ เสี่ยงกดผิดและทำให้หน้าแน่น
5. ไอคอนของแผนที่บางส่วนไม่ใช่ทางเข้าหมวดเครื่องมือที่ชัดเจน และผู้ใช้ใหม่อาจไม่รู้ว่าควรกดตรงไหนก่อน
6. ต้องคงระบบบันทึกอัตโนมัติเดิมไว้และแสดงสถานะให้เข้าใจง่าย ไม่ควรสร้างกลไกบันทึกซ้ำซ้อนโดยไม่จำเป็น

## 2. รูปแบบหน้าจอเป้าหมาย

### โครงสร้างหลัก

- **พื้นที่แผนที่:** เป็นพื้นที่ทำงานหลัก เห็นขอบเขตและจุดปลูกชัดเจน
- **แถบไอคอนประจำที่:** เป็นทางเข้าหมวดหลักตลอดเวลา โดยมีไอคอนและชื่อภาษาไทย ไม่ใช้ไอคอนล้วน
- **แผงเครื่องมือเฉพาะหมวด:** เมื่อแตะหมวด ให้แสดงเฉพาะคำสั่งของหมวดนั้น ไม่แสดงทุกการตั้งค่าพร้อมกัน
- **แถบคำสั่งสำคัญ:** แสดงสถานะงานและปุ่มหลักที่เกี่ยวข้องกับขั้นตอนปัจจุบัน เช่น “วาดขอบเขต”, “สร้างจุดปลูก” หรือ “ดูรายงาน”
- **สถานะบันทึก:** แสดงให้เห็นชัดว่าบันทึกในอุปกรณ์แล้วหรือยัง และเตือนเมื่อไม่สามารถบันทึกได้

### หมวดไอคอนที่เสนอ

1. **แปลง** — ชื่อแปลง, ตำแหน่งแปลง, ใช้ตำแหน่งมือถือ, พื้นที่และขอบเขต
2. **วาด/แก้ไข** — วาดขอบเขต, แก้ขอบเขต, ยกเลิกการวาด, เลือกและลบต้น, ย้อนกลับการลบ
3. **ปลูกปาล์ม** — สร้าง/สร้างใหม่จุดปลูก, จำนวนต้นจริง, ตรวจระยะห่าง และสรุปผล
4. **ตั้งค่า** — ระยะปลูก, หมุนแนวแถว, เว้นระยะจากขอบแปลง, ราคาต้นกล้า
5. **รายงาน** — ดูสรุป, PDF/พิมพ์รายงาน, CSV, GeoJSON
6. **เพิ่มเติม** — วิธีใช้, สถานะการบันทึก, ล้างแผน/เริ่มใหม่ โดยการล้างต้องมีหน้าต่างยืนยัน

บนมือถือใช้แถบไอคอนติดขอบล่างหรือขอบที่ไม่บังแผนที่ พร้อมแผงหมวดที่เปิด/ปิดได้ บนคอมพิวเตอร์ใช้แถบหมวดที่มองเห็นตลอดเวลาและแผงเนื้อหาข้างแผนที่ได้ ทั้งสองแบบใช้โครงสร้างและชื่อหมวดเดียวกัน

> หลักการเข้าถึง: ไอคอนทุกตัวต้องมีชื่อภาษาไทย, tooltip/คำอธิบายเมื่อเหมาะสม, สถานะเลือกอยู่ที่มองเห็นได้ และพื้นที่แตะใหญ่พอสำหรับมือถือ ห้ามซ่อนคำสั่งสำคัญไว้หลังไอคอนที่ไม่มีคำอธิบาย

## 3. แผนพัฒนาเป็นเฟส

## Phase 0 — สำรวจและล็อกพฤติกรรมเดิม

**เป้าหมาย:** รู้ว่าคำสั่งใดต้องรักษาพฤติกรรมเดิมก่อนเปลี่ยนโครงสร้าง UI

งาน:
- ทำรายการ element ID, event listener และฟังก์ชันที่แต่ละปุ่มเรียกใช้
- ระบุ dependency ระหว่าง `index.html`, `app.js`, `calculator.js`, `exporter.js`
- บันทึกพฤติกรรมปัจจุบันของการวาด/แก้ขอบเขต, สร้างกริด, ลากจุด, ลบจุด, undo, คำนวณพื้นที่/จำนวนต้น, LocalStorage และส่งออกไฟล์
- ระบุปุ่มที่ต้องคง ID เดิมไว้ หรือเปลี่ยนการผูก event อย่างมีแผน เพื่อป้องกันปุ่มเดิมหยุดทำงาน
- ตรวจการทำงานบนมือถือและ Desktop ก่อนเริ่มแก้จริง

ไฟล์หลัก: ทุกไฟล์ที่ระบุในส่วนตรวจโค้ด

เกณฑ์ตรวจรับ:
- มีรายการพฤติกรรมเดิมและรายการปุ่มครบ
- ไม่มีการเปลี่ยนสูตรคำนวณในเฟสนี้
- มี baseline สำหรับเทียบก่อน/หลัง

## Phase 1 — จัดหมวดเครื่องมือและสร้างแถบไอคอน

**เป้าหมาย:** ผู้ใช้เข้าถึงหมวดสำคัญได้โดยไม่ต้องเลื่อนหาเครื่องมือที่กระจายอยู่

งาน:
- ปรับโครงสร้าง `index.html` ให้มีแถบหมวดและพื้นที่เนื้อหาของแต่ละหมวด
- สร้างหมวด “แปลง”, “วาด/แก้ไข”, “ปลูกปาล์ม”, “ตั้งค่า”, “รายงาน” และ “เพิ่มเติม”
- ใช้ปุ่มจริงที่มี `type="button"`, label ภาษาไทย และ `aria-label`/สถานะเลือกที่เหมาะสม
- ย้าย/จัดกลุ่มองค์ประกอบเดิมโดยคง ID เดิมให้มากที่สุด เพื่อลดความเสี่ยงที่ event listener ใน JS จะเสีย
- ให้เปิดได้ทีละหมวด และจำกัดการแสดงเนื้อหาเฉพาะหมวดที่เลือก
- คงแถบสถานะและสถานะบันทึกให้มองเห็นได้โดยไม่ต้องเปิดหมวด “เพิ่มเติม”
- ให้ปุ่ม “สร้างจุดปลูก” เป็นคำสั่งหลักที่เห็นชัดเมื่อมีขอบเขตแปลงพร้อม
- ปุ่ม “ล้างทั้งหมด” ต้องอยู่ในหมวดเพิ่มเติมและถามยืนยันก่อนทำงาน

ไฟล์หลัก: `index.html`, `css/style.css`, ส่วนจัดการ UI ใน `js/app.js`

เกณฑ์ตรวจรับ:
- เครื่องมือหลักทุกตัวอยู่ในหมวดที่คาดเดาได้
- ไม่มีปุ่มหลักซ้ำหลายตำแหน่งโดยไม่จำเป็น
- ไม่มี element ID ซ้ำ
- ปุ่มทุกตัวเรียกการทำงานเดิมได้
- สามารถสลับหมวดโดยไม่รีเซ็ตแผนหรือค่าที่กรอก

## Phase 2 — ปรับ UX มือถือและ Desktop

**เป้าหมาย:** แผนที่ยังใช้งานได้สะดวก ขณะเดียวกันก็เข้าถึงเครื่องมือได้ตลอด

งาน:
- มือถือ: ใช้แถบไอคอนแบบติดขอบจอและแผงหมวดแบบ bottom sheet ที่เปิด/ย่อได้
- Desktop: ใช้แถบหมวดที่เห็นชัด พร้อมแผงรายละเอียดข้างแผนที่ ไม่บังคับให้เลื่อนผ่านทุกหมวด
- ป้องกันแผงบังปุ่มซูม เครื่องมือวาด หรือพื้นที่แผนที่ที่กำลังทำงาน
- ปรับขนาดปุ่ม พื้นที่สัมผัส ช่องกรอก และระยะห่างให้เหมาะกับนิ้ว
- เพิ่ม focus state สำหรับคีย์บอร์ดและ contrast ที่อ่านง่าย
- รองรับ safe-area ของมือถือ และทดสอบทั้งแนวตั้ง/แนวนอน
- คงการย่อแผงอัตโนมัติเมื่อเริ่มวาดแปลง หากช่วยให้เห็นแผนที่มากขึ้น แต่ต้องไม่ทำให้ผู้ใช้เสียตำแหน่งการทำงาน
- ตรวจให้แผนที่ปรับขนาดหลังเปิด/ปิดแผง เพื่อไม่ให้แผนที่เพี้ยน

ไฟล์หลัก: `css/style.css`, `index.html`, `js/app.js`

เกณฑ์ตรวจรับ:
- ที่ความกว้างมือถือทั่วไป ผู้ใช้เข้าถึงหมวดได้โดยไม่ต้องเลื่อนแผงยาวเพื่อหาปุ่มหลัก
- แผนที่ไม่ถูกแผงบังจนวาดขอบเขตไม่ได้
- Desktop ไม่เกิดการบีบแผนที่หรือแผงเครื่องมือจนใช้งานยาก
- ปุ่มและข้อความไม่ล้นหรือซ้อนกันในแนวตั้ง/แนวนอน

## Phase 3 — ทำขั้นตอนใช้งานให้ชัดเจน

**เป้าหมาย:** ผู้ใช้ใหม่เข้าใจว่าต้องทำอะไรต่อ โดยไม่ต้องอ่านคู่มือยาวก่อน

งาน:
- แสดงขั้นตอนแบบสั้น: 1) ระบุแปลง 2) วาดขอบเขต 3) สร้างจุดปลูก 4) ตรวจและแก้ไข 5) ส่งออกรายงาน
- แสดงสถานะขั้นตอนตามข้อมูลจริง เช่น “ยังไม่ได้วาดขอบเขต”, “พร้อมสร้างจุดปลูก”, “สร้างจุดปลูกแล้ว”
- ปุ่มที่ยังใช้ไม่ได้ให้แสดงเหตุผลสั้น ๆ ไม่ใช่ disabled โดยไม่มีคำอธิบาย
- เมื่อสร้างจุดปลูกสำเร็จ แสดงจำนวนต้นจริงและคำแนะนำขั้นต่อไป
- เมื่อแก้ระยะปลูกแล้วมีผลกับกริดเดิม ให้เตือนและอธิบายผลก่อนล้าง/สร้างกริดใหม่
- แยก “ตำแหน่งมือถือ” ออกจาก “ตำแหน่งแปลง” ให้ชัดเจนเหมือนเดิม
- ข้อความผิดพลาดต้องเป็นภาษาไทย เข้าใจง่าย และบอกวิธีแก้ที่ทำได้

ไฟล์หลัก: `index.html`, `js/app.js`, `js/exporter.js`

เกณฑ์ตรวจรับ:
- ผู้ใช้ใหม่สามารถทำตามขั้นตอนได้โดยไม่ต้องเดาว่าปุ่มใดต้องกดก่อน
- สถานะที่แสดงตรงกับสถานะจริงของแผน
- การแจ้งเตือนไม่ทำให้ข้อมูลแผนหายหรือถูกเปลี่ยนโดยไม่ตั้งใจ

## Phase 4 — ตั้งค่าและรายงานโดยไม่ทำให้หน้าหลักรก

**เป้าหมาย:** เก็บการตั้งค่าที่ใช้ไม่บ่อยและคำสั่งส่งออกไว้เป็นหมวด แต่เรียกใช้งานได้ง่าย

งาน:
- รวมระยะปลูก, หมุนแนวแถว, ระยะขอบ และราคาต้นกล้าไว้ใน “ตั้งค่า”
- แสดงค่าปัจจุบันและหน่วยชัดเจน เช่น เมตร, องศา, บาท/ต้น
- รวม PDF, พิมพ์รายงาน, CSV และ GeoJSON ไว้ใน “รายงาน”
- ทำให้ PDF/พิมพ์รายงานเป็นตัวเลือกหลัก ส่วน CSV/GeoJSON เป็นตัวเลือกสำหรับนำข้อมูลไปใช้ต่อ
- ปุ่มส่งออกต้องแสดงสถานะกำลังทำงาน/สำเร็จ/ล้มเหลว และไม่เปิดใช้งานเมื่อไม่มีข้อมูลที่จำเป็น
- รักษา LocalStorage อัตโนมัติเดิม เพิ่มข้อความสถานะบันทึกที่เข้าใจง่าย และจัดการกรณีพื้นที่จัดเก็บเต็ม/ถูกปิดกั้น
- อธิบายสั้น ๆ ว่าข้อมูลอยู่ในเบราว์เซอร์ของอุปกรณ์นี้ ไม่ได้ซิงก์ไปอุปกรณ์อื่นโดยอัตโนมัติ

ไฟล์หลัก: `index.html`, `css/style.css`, `js/app.js`, `js/exporter.js`

เกณฑ์ตรวจรับ:
- การเปลี่ยนหมวดไม่ทำให้ค่าตั้งต้นหรือข้อมูลที่กรอกหาย
- PDF, CSV และ GeoJSON ยังส่งออกข้อมูลที่ตรงกับแผนปัจจุบัน
- ผู้ใช้แยกได้ว่าการบันทึกอัตโนมัติในเครื่องไม่เหมือนกับการดาวน์โหลดไฟล์สำรอง

## Phase 5 — ทดสอบการคำนวณและ regression

**เป้าหมาย:** ยืนยันว่าเปลี่ยนหน้าจอแล้วการคำนวณและเครื่องมือเดิมยังถูกต้อง

กรณีทดสอบขั้นต่ำ:
- วาดแปลงสี่เหลี่ยมและแปลงรูปร่างไม่สม่ำเสมอ
- แก้ไขและลบขอบเขต
- สร้างจุดปลูกด้วยค่าระยะเริ่มต้น 9 เมตร และค่าระยะอื่นที่รองรับ
- เปลี่ยนมุมหมุนและระยะขอบ แล้วตรวจจำนวนจุดปลูก
- ลากจุดปลูก ตรวจการเตือนจุดใกล้กัน และลบจุด
- Undo หลังลบจุด
- เปลี่ยนหมวดไปมาแล้วตรวจว่าแผนและค่าต่าง ๆ ไม่หาย
- รีเฟรชหน้าเว็บและตรวจการกู้คืน LocalStorage
- ทดสอบกรณี LocalStorage ใช้งานไม่ได้
- ส่งออก PDF, พิมพ์รายงาน, CSV และ GeoJSON แล้วตรวจข้อมูลและพิกัด
- ทดสอบการอนุญาต/ปฏิเสธตำแหน่ง GPS และการใช้งานต่อโดยไม่ให้สิทธิ์
- ทดสอบมือถือ Android, Desktop และขนาดจอแคบ

เกณฑ์ตรวจรับ:
- ไม่มี regression ในการวาด/คำนวณ/แก้ไข/ลบ/undo/ส่งออก
- ไม่มีข้อมูลสูญหายเมื่อสลับหมวดหรือย่อ/ขยายแผง
- ข้อผิดพลาดที่เกิดขึ้นมีข้อความที่ผู้ใช้เข้าใจได้
- บันทึกผลทดสอบและข้อบกพร่องที่ยังเหลือไว้ใน GitHub ก่อนประกาศเสร็จ

## 4. ลำดับการทำงานที่แนะนำ

1. Phase 0 — สำรวจและล็อกพฤติกรรมเดิม
2. Phase 1 — แถบไอคอนและจัดหมวด
3. Phase 2 — ปรับมือถือและ Desktop
4. Phase 3 — ขั้นตอนใช้งานและสถานะ
5. Phase 4 — ตั้งค่า/รายงาน/สถานะบันทึก
6. Phase 5 — regression และทดสอบบนอุปกรณ์จริง

ควรทำทีละเฟสและทดสอบหลังแต่ละเฟส อย่ารวมการเปลี่ยน UI, สูตรคำนวณ และรูปแบบข้อมูลไว้ในชุดแก้ไขเดียวโดยไม่จำเป็น

## 5. ขอบเขตที่ยังไม่ควรเพิ่ม

เพื่อให้เหมาะกับการใช้งานในครอบครัว 3–4 คน และไม่เพิ่มความซับซ้อนเกินจำเป็น ในรอบนี้ยังไม่ต้องเพิ่ม:
- ระบบสมาชิก/ล็อกอิน
- Backend หรือฐานข้อมูลใหม่
- ระบบซิงก์ข้ามอุปกรณ์
- ไลบรารี UI ขนาดใหญ่ หาก HTML/CSS/JavaScript เดิมทำได้
- การเปลี่ยนสูตรคำนวณโดยไม่ผ่านการทดสอบแยก

## 7. นิยามว่าเสร็จแล้ว

งาน UI รอบนี้จะถือว่าเสร็จเมื่อผู้ใช้เข้าถึงเครื่องมือหลักจากหมวดที่เห็นได้ทันที ไม่ต้องไล่เลื่อนหา, ชื่อหมวดและปุ่มเข้าใจง่ายเป็นภาษาไทย, แผนที่ใช้ได้ทั้งมือถือและคอมพิวเตอร์, การบันทึก/ส่งออกแสดงสถานะตรงตามจริง และฟังก์ชันเดิมทั้งหมดผ่านรายการทดสอบ regression แล้ว

**หมายเหตุ:** เอกสารนี้เป็น roadmap สำหรับการพัฒนา ไม่ใช่การยืนยันว่ามีการเปลี่ยน UI หรือทดสอบบนอุปกรณ์จริงแล้ว
