# Roadmap UX รอบถัดไป — สวนปาล์ม V4
อัปเดต: 2026-10-23
รีโพ: https://github.com/aodxx/suan-palm
อ้างอิงสถานะโค้ด: `docs/PHASE-0-5-ACCEPTANCE.md`, `index.html`, `css/style.css`, `js/app.js`
อ้างอิงรูปแบบ: ภาพแอปตัวอย่างจากผู้ใช้ (แผนที่เด่น, ปุ่มลอยสำหรับคำสั่งหลัก, แถบนำทางด้านล่าง) และแอปงานแผนที่/วัดแปลงที่อ้างถึงท้ายเอกสาร

> เป้าหมายรอบนี้ไม่ใช่เพิ่มฟีเจอร์ให้มากขึ้น แต่ลดขั้นตอนที่ผู้ใช้ต้องคิด เปิดแผง และสลับหมวด เพื่อทำงานเดิมให้จบได้เร็วขึ้น โดยคงระบบคำนวณ แผนที่ และข้อมูลเดิมไว้

## 1. สรุปการตัดสินใจด้าน UX

### สิ่งที่ยึดจากภาพตัวอย่าง
- แผนที่เป็นพื้นที่หลักของหน้าจอ
- คำสั่งที่ใช้บ่อยวางลอยอยู่ใกล้มือบนแผนที่ เช่น เพิ่ม/สร้าง, ย้อนกลับ และบันทึกหรือส่งออกตามบริบท
- แถบนำทางหลักอยู่ในตำแหน่งคงที่และเข้าถึงได้โดยไม่ต้องเปิดแผงใหญ่
- ใช้ปุ่มหลักที่เด่นเพียงหนึ่งปุ่มในแต่ละสถานการณ์

### สิ่งที่ไม่ควรลอกมาโดยตรง
- ไม่คัดลอกสี สัญลักษณ์ หรือตำแหน่งทุกอย่างโดยไม่ทดสอบกับงานปลูกปาล์ม
- ไม่แสดงปุ่มทุกคำสั่งพร้อมกันจนบังแผนที่
- ไม่สร้าง bottom navigation และแท็บชุดที่สองซึ่งซ้ำหน้าที่กัน
- ไม่ใช้ไอคอนล้วนกับคำสั่งที่ผู้ใช้ใหม่อาจเข้าใจผิด

### หลักการเป้าหมาย
1. งานที่ทำต่อเนื่องกันควรทำได้ในมุมมองเดียว เช่น วาดขอบเขต → สร้างจุดปลูก → ตรวจ/แก้จุด
2. แสดงคำสั่งตามบริบท: แสดงเฉพาะคำสั่งที่ใช้ได้ในสถานะปัจจุบัน
3. แยก “คำสั่งทำงานบนแผนที่” ออกจาก “การตั้งค่าระบบ” และ “รายงาน” ให้ชัด
4. สถานะบันทึกและความผิดพลาดต้องเห็นได้โดยไม่ต้องเปิดหมวดเพิ่มเติม
5. เก็บ element IDs, event handlers, สูตรคำนวณ, LocalStorage schema และรูปแบบไฟล์ส่งออกเดิมไว้ เว้นแต่มีเหตุผลและการทดสอบเฉพาะ
6. การเปลี่ยน UI ต้องไม่ทำให้ผู้ใช้ต้องสร้างแปลงหรือจุดปลูกใหม่เพียงเพราะสลับหน้าจอ

## 3. Roadmap รอบถัดไป

## Phase 6 — ตรวจประสบการณ์จริงและระบุจุดติดขัด
**เป้าหมาย:** หาความยุ่งยากจาก flow จริงก่อนเปลี่ยนหน้าจออีกครั้ง

งาน:
- ทำรายการงานสำคัญ 4 งาน: (A) เริ่มแปลงใหม่และวาดขอบเขต (B) สร้างจุดปลูก (C) แก้/ลบ/ย้อนกลับจุด (D) ดูสรุปและส่งออกรายงาน
- วัดจำนวนแตะ จำนวนครั้งที่เปิด/ย่อแผง และจำนวนครั้งที่เปลี่ยนหมวดสำหรับแต่ละงาน
- ตรวจบนมือถือ Android ขนาดจอจริง รวมแนวตั้ง/แนวนอน และตรวจ Desktop แยกกัน
- ตรวจว่าตอนแผงย่อ ผู้ใช้ยังเห็นคำสั่งหลัก, สถานะ, GPS และการบันทึกเพียงพอหรือไม่
- ทำตาราง `ปัญหา → หลักฐาน → ผลกระทบ → แนวทางแก้ → เกณฑ์ผ่าน`
- ห้ามแก้สูตรคำนวณหรือ schema ข้อมูลในเฟสนี้

ไฟล์: `docs/UX-AUDIT-NEXT.md`, `docs/PHASE-0-5-ACCEPTANCE.md` (อัปเดตผลอุปกรณ์จริง)

เกณฑ์ตรวจรับ:
- มีผลตรวจจาก Android จริงหรือระบุชัดว่าส่วนใดต้องให้ผู้ใช้ทดสอบเอง
- ปัญหาทุกข้อมีหลักฐานและลำดับความสำคัญ
- มี baseline ของจำนวนแตะ/การสลับหมวดก่อนเปลี่ยน UI

## Phase 7 — ออกแบบ Map-first และคำสั่งตามบริบท
**เป้าหมาย:** ลดการเปิด/ปิดแผงและไม่ต้องสลับหมวดระหว่างงานต่อเนื่อง

แนวทางออกแบบเพื่อทดลอง (ยังไม่ใช่ข้อสรุปก่อนทดสอบ):
- แผนที่เป็นหน้าหลักและเห็นได้เกือบเต็มจอ
- มีแถบนำทางหลักเพียงชุดเดียว ถ้าจะมี bottom navigation ต้องไม่ซ้ำกับแท็บ 6 หมวดเดิม
- มีปุ่มลอยหลักเพียงหนึ่งปุ่มตามสถานะ เช่น “วาดขอบเขต”, “สร้างจุดปลูก”, หรือ “เสร็จ/รายงาน”
- เมื่ออยู่ในโหมดวาดหรือแก้ไข ให้แสดงคำสั่งที่เกี่ยวข้องใกล้แผนที่ เช่น ยกเลิก/ย้อนกลับ/บันทึกการแก้ไข โดยไม่แสดงคำสั่งที่ใช้ไม่ได้
- คำสั่งรอง เช่น ชั้นแผนที่, GPS, ตั้งค่า, รายงาน อยู่ในพื้นที่เข้าถึงง่ายแต่ไม่บังแผนที่
- ใช้ icon pack ที่มีใน `assets/icons/ui-3d/` และมีชื่อไทยกำกับ
- ทำต้นแบบอย่างน้อย 2 ทางเลือก (A: แถบนำทางคงที่ + แผงบริบท, B: แผนที่ + action dock) แล้วเปรียบเทียบก่อนเลือก

ไฟล์: `index.html`, `css/style.css`, ส่วน UI ใน `js/app.js`; เพิ่ม mockup/บันทึกตัดสินใจใน `docs/UX-AUDIT-NEXT.md`

ข้อห้าม:
- ห้ามผูก event listener ใหม่ซ้ำกับ handler เดิม
- ห้ามย้ายการควบคุมของ Leaflet โดยไม่ตรวจ touch usability
- ห้ามเพิ่มปุ่ม “บันทึก” ที่ทำให้ผู้ใช้เข้าใจว่าระบบ auto-save เดิมไม่ทำงาน; ถ้าปุ่มนั้นหมายถึง export หรือยืนยันการแก้ไข ต้องตั้งชื่อให้ตรง

เกณฑ์ตรวจรับ:
- ไม่มี navigation ซ้ำสองชั้น
- งานวาด → สร้างจุด → ตรวจแก้ ทำได้โดยไม่ต้องเปิดหมวดอื่นระหว่างทาง หรือมีเหตุผลชัดเจนสำหรับการเปลี่ยนมุมมอง
- แผนที่ยังใช้ drag/pinch/zoom ได้ตามปกติ

## Phase 8 — ปรับ workflow สร้างและแก้จุดปลูก
**เป้าหมาย:** ทำให้งานหลักของสวนปาล์มเร็วและเข้าใจง่ายกว่าการจัดเมนูทั่วไป

งาน:
- หลังวาดขอบเขตเสร็จ แสดงพื้นที่และปุ่มสร้างจุดปลูกโดยอัตโนมัติ
- หลังสร้างสำเร็จ แสดงจำนวนต้นจริงและเปิดคำสั่งแก้ไขที่ใช้บ่อย โดยไม่เปลี่ยนหน้าจอโดยไม่จำเป็น
- ทำให้การเลือกจุด ลากจุด ลบ และ Undo มีคำอธิบายสั้นที่ตรงกับ interaction จริง
- แยก “สร้างใหม่แทนที่กริดเดิม” ออกจาก “แก้จุดที่มีอยู่” ให้เห็นชัดก่อนดำเนินการ
- เมื่อค่าระยะ/มุม/ระยะขอบเปลี่ยน ให้แสดงผลกระทบและขอคำยืนยันเฉพาะเมื่อจำเป็น
- ห้ามให้การเปิดแผงหรือเปลี่ยนหมวดล้าง state/selection โดยไม่ตั้งใจ

ไฟล์: `index.html`, `css/style.css`, `js/app.js`

เกณฑ์ตรวจรับ:
- ผู้ใช้เห็นผลหลังแต่ละ action อย่างชัดเจน
- สร้างใหม่ไม่ทำให้จุดที่ลากแก้ไว้หายโดยไม่เตือน
- Undo และการแจ้งเตือนระยะห่างยังทำงาน
- ไม่มีการเปลี่ยนสูตรคำนวณโดยไม่มีชุดทดสอบเฉพาะ

## Phase 9 — ลดความหนาแน่นของหน้าจอและทำ UI ให้สม่ำเสมอ
**เป้าหมาย:** ลดสิ่งที่ต้องอ่าน/จำ โดยยังคงเข้าถึงการตั้งค่าและรายงานได้

งาน:
- ยุบ workflow 5 ขั้นเป็นสถานะสั้น ๆ พร้อมขยายรายละเอียดเมื่อผู้ใช้ต้องการ
- ใช้ระบบขนาดไอคอน ปุ่ม ระยะห่าง และสีสถานะชุดเดียวกัน
- ไอคอนต้องมีชื่อไทยที่มองเห็นได้ หรือ accessible name ที่ชัดเจน
- แยกคำสั่งอันตราย เช่น ล้างแผน ออกจากคำสั่งประจำและต้องยืนยัน
- แสดงเฉพาะการตั้งค่าที่เกี่ยวข้องกับงานปัจจุบัน; ค่าใช้ไม่บ่อยอยู่ใน settings
- ตรวจภาษาไทยบนหน้าจอแคบ การตัดคำ ขนาดปุ่ม และ contrast
- คง status และ storage feedback ไว้ในตำแหน่งคงที่โดยไม่กินพื้นที่เกินจำเป็น

ไฟล์: `index.html`, `css/style.css`, `assets/icons/ui-3d/`, `README.md`

เกณฑ์ตรวจรับ:
- ไม่มี label/ปุ่มซ้ำซ้อนโดยไม่มีเหตุผล
- ทุกปุ่มหลักมีชื่อที่เข้าใจได้
- ไม่มีข้อความ/ปุ่มล้นหรือทับแผนที่บน viewport ที่กำหนด

## Phase 10 — ทดสอบเปรียบเทียบและปิดงาน
**เป้าหมาย:** ตัดสินจากผลใช้งาน ไม่ใช่ความรู้สึกจากภาพหน้าจออย่างเดียว

กรณีทดสอบ:
- ทำงาน A–D ใน Phase 6 บน Android และ Desktop
- ทดสอบจอแคบ, แนวนอน, safe-area, การเปิด/ย่อแผง และการหมุนจอ
- วาด/แก้/ลบ polygon; สร้างกริด; ลาก/ลบ/Undo จุด; ตรวจ near-distance warning
- เปลี่ยนหมวด/เปิดเมนูโดยตรวจว่าข้อมูลและตำแหน่งแผนไม่หาย
- ตรวจ LocalStorage หลัง refresh และกรณี storage ใช้ไม่ได้
- ทดสอบ GPS ทั้งอนุญาต/ปฏิเสธ
- ดาวน์โหลด PDF, Print, CSV, GeoJSON และตรวจเนื้อหา/พิกัด
- ตรวจ SVG ทุกไฟล์ที่ใช้งานจริงว่าโหลดได้บน GitHub Pages และไม่เกิด 404
- รัน `node --test tests/regression.test.cjs` และ `node --check` สำหรับ JavaScript
- เปรียบเทียบจำนวนแตะและจำนวนครั้งเปิด/ปิดแผงกับ baseline

เกณฑ์ตรวจรับ:
- ไม่มี regression ในฟังก์ชันเดิม
- งานหลักใช้จำนวนแตะ/การสลับแผงลดลงจาก baseline หรือมีเหตุผลพร้อมหลักฐานหากลดไม่ได้
- ผู้ใช้ทดสอบจริงยืนยันว่าทำงานหลักได้คล่องขึ้น
- บันทึกผลผ่าน/ไม่ผ่านและข้อจำกัดคงเหลือใน GitHub ก่อนประกาศเสร็จ

## 4. ลำดับการดำเนินงาน
1. Phase 6: ตรวจ flow จริงและรวบรวมหลักฐาน
2. Phase 7: ทดลองโครงสร้าง Map-first 2 แบบและเลือกแบบที่ลดการสลับมุมมองได้มากที่สุด
3. Phase 8: ปรับงานสร้าง/แก้จุดปลูก
4. Phase 9: ลดความหนาแน่นและทำ UI ให้สม่ำเสมอ
5. Phase 10: ทดสอบเทียบ baseline และยืนยันบนอุปกรณ์จริง

ทำทีละเฟส ไม่เปลี่ยน UI ใหญ่หลายส่วนพร้อมกัน และอย่าเริ่ม Phase 8 ก่อนตัดสินใจโครงสร้างจาก Phase 7

## 5. เกณฑ์ความสำเร็จของรอบนี้
- แผนที่เป็นพื้นที่หลักบนมือถือ
- งานหลักไม่ต้องสลับแถบหรือเปิด/ปิดแผงซ้ำ ๆ
- มีปุ่มหลักตามบริบท ไม่แสดงคำสั่งทุกอย่างพร้อมกัน
- ไม่มี navigation ซ้ำซ้อน
- ไม่สูญเสียข้อมูลหรือเปลี่ยนผลคำนวณเดิม
- ผ่าน regression และการทดสอบ Android จริง พร้อมบันทึกหลักฐาน
